## Required corrections and additions

1. **Resource deep-copy scope needs an explicit Script exception.** `main.json`, `classes/class_resource.rst`, correctly distinguishes internal and external subresources, but its compact `duplicate_deepALL explicit externalcopy` wording must not imply that every nested Resource becomes independent. [Resource::_duplicate_recursive](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/io/resource.cpp#L278) excludes `Script` from normal subresource-mode duplication, including ALL, after deciding whether duplication is eligible. ALWAYS/NEVER property usage flags are checked separately before that branch. `_duplicate` also reuses the attached script and copies only STORAGE properties. Add: normal deep-copy modes retain Script references; property usage overrides and constructor requirements are separate exceptions. Test runtime state rather than assuming detached scripts or arbitrary objects. The architecture report's warning about external resources is correct; strengthen “local” to “built-in/internal” to distinguish this rule from `resource_local_to_scene`.

2. **HDR buffer activation does not guarantee a true `use_hdr_2d` getter.** `extension.json`, `classes/class_displayserver.rst`, says requesting HDR internally enables main `Viewport.use_hdr_2d`; `render.json`, `classes/class_projectsettings.rst`, uses similar wording. [Window::_update_viewport_for_hdr_output](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/main/window.cpp#L1980) directly updates the RenderingServer viewport when the stored Viewport setting is false. It does not call `Viewport::set_use_hdr_2d` or change the Viewport's stored boolean. Thus the internal buffer may be HDR while the property getter remains false. Replace wording with “forces internal HDR 2D rendering for that Window's viewport”; keep explicit settings for other SubViewports. Do not assert successful activation solely from the getter. `Window::set_hdr_output_requested` operates on each Window, so “main only” is a tutorial convention rather than the method's full scope. Requested, supported and enabled display states still require separate queries and real output evidence.

3. **Two ledger mappings omit important operational owners.** `extension.json`, `classes/class_@gdscript.rst`, contains the RPC conclusion but lacks `godot-multiplayer` in its skills array. Add it. `tutorials/plugins/running_code_in_the_editor.rst` maps only `godot-editor-tools`, whereas its persisted-node ownership and Resource change-handler conclusions also serve `godot-scenes` and `godot-data`; the initial extensions report already names those owners. Add the two mappings. This is a routing omission, not missing source reading.

4. **Resolve the TextEdit backspace ambiguity before recipe reuse.** `extension.json`, `classes/class_textedit.rst`, correctly flags contradictory prose. [TextEdit backspace implementation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/gui/text_edit.cpp#L7871) removes one codepoint when mid-grapheme mode is enabled OR composite-character deletion is disabled; otherwise it uses the previous composite-character boundary. The unconditional documentation note that Backspace always removes an individual component is stale for these settings. Record the source resolution and retain an actual emoji/combining-character test requirement.

## Confirmed conclusions

- **Default RPC reliability is correct.** [GDScript annotation registration](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/modules/gdscript/gdscript_parser.cpp#L187) supplies authority, call_remote, reliable and channel 0. [C# RpcAttribute](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/modules/mono/glue/GodotSharp/GodotSharp/Core/Attributes/RpcAttribute.cs#L27) defaults transfer to Reliable and its constructor defaults mode to Authority. Main and extension ledgers agree. SceneReplicationConfig's ALWAYS/unreliable behavior is a different replication contract, not an RPC contradiction. The Context7 RPC response confirms the same defaults, but includes an unrelated suspicious `_init` sentence; do not transfer that sentence into Skills.
- **Resource versus container duplication is correctly separated.** `Resource.duplicate(true)` recurses through arrays/dictionaries and duplicates eligible internal resources; `Array.duplicate(true)` and `Dictionary.duplicate(true)` retaining resource references are different APIs. Do not “fix” their ledgers to make them equivalent. Shared-reference identity within a Resource duplication session is preserved by the remap cache.
- **Editor docking and lifecycle conclusions match source.** [EditorPlugin add/remove_dock](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/editor/plugins/editor_plugin.cpp#L132) uses EditorDockManager. Enable runs after tree insertion; disable is the last project-disable callback. UI registration/removal belongs to paired tree lifecycle; autoload registration/removal belongs to enable/disable as described. Free only owned controls after removal. This establishes API wiring, not repeated-toggle acceptance.
- **Tool-script inheritance and persistence conclusions are sound.** The pinned editor tutorial explicitly requires tool annotation in extending scripts, explicit Resource change emission/replacement disconnection, edited-root ownership for saved added nodes, and scene unsaved marking or EditorUndoRedoManager. Preserve inherited-scene boundaries and user's editor settings.
- **Language execution limits are honest.** The extensions report distinguishes installed .NET/compiler presence from .NET Godot, package restore, ABI-compatible extension builds and actual editor lifecycle. No C# or GDExtension pass is claimed. The TextEdit C# menu example remains unsafe to copy without generated binding and compiler verification; native PopupMenu exposes an integer signal, but the generated C# files are absent from this source snapshot, so this review does not pretend to have tested its delegate signature.
